# AI-agent-memory benchmarking methodologies — an implementable catalogue

**Status:** research (S1 of `docs/plans/2026-07-04-competitive-benchmark.md`) · **Researched:** 2026-07-04 · **Method:** multi-source web research (~30 search + fetch passes) across arXiv, ACL Anthology, GitHub, vendor blogs, and independent critique sites; primary sources fetched directly where possible; claims adversarially cross-checked (vendor number vs. benchmark's own definition, vendor number vs. independent dispute) before inclusion. This file is input to S2–S4 of the competitive-benchmark plan; it does not itself run any benchmark.

**Scope note:** this catalogue evaluates *methods*, not iranti's actual scores. No iranti code was modified to produce this file, and none of the numbers below are iranti's — they are the field's, quoted for calibration and adversarial-verification practice.

## (a) Executive summary

The AI-memory benchmarking field has two well-established, ACL/ICLR-peer-reviewed anchors — **LoCoMo** (ACL 2024, conversational QA over 10 very-long dialogues) and **LongMemEval** (ICLR 2025, 500 questions across 5–6 memory abilities including abstention) — plus a fast-multiplying 2025–2026 wave of successor and adjacent benchmarks (**BEAM**, **MemBench**, **MemoryArena**, **LongMemEval-V2**, **SWE-ContextBench**, and several contradiction/temporal-specific probes like STALE and TOKI) that each isolate a narrower capability LoCoMo/LongMemEval under-tests. Both anchors are showing real strain: a rigorous 2026 critique demonstrates that switching only the *credited scoring target* (raw turns vs. transformed facts/summaries) flips system rankings on 83–94% of LoCoMo/LongMemEval-S queries without the retrieved content changing at all, and **MemoryArena** shows systems near-saturated on LoCoMo collapsing to 40–60% the moment memory has to *drive a decision* rather than just answer a question — meaning LoCoMo/LongMemEval numbers, including the headline 88–96% range vendors now report, measure something real but narrower than "is this memory system good," and every self-reported vendor number in this space needs independent scrutiny by default: this report documents a live, GitHub-issue-level dispute in which Zep's own claimed 84% LoCoMo accuracy was shown to be 58.44% under a corrected methodology, and MemPalace's own team disclosed a LoCoMo top-k configuration that bypassed retrieval testing entirely. For iranti specifically, the field has **no standard benchmark for coding-agent memory** at all — every existing benchmark is conversational-chat-shaped — which is both the report's clearest gap and iranti's clearest opportunity: §(d) below specifies a concrete, buildable cross-session task-continuity methodology (a "SWE-bench-with-memory" framing) that no competitor in the named set (Mem0/Zep/ByteRover/Shodh/ai-mem/Obsidian) is currently measured against, alongside a recommended 3–4-method minimal fair suite (§c) that reuses published judge prompts so every system in the shared corpus gets scored identically.

### The Obsidian apples-to-oranges boundary, made explicit

**Fair to test (Obsidian has a real, comparable mechanism):**
- Retrieval precision/recall/F1@k over a shared, hand-authored vault (its full-text search is BM25-like per multiple 2026 community sources — [VaultSearch forum thread](https://forum.obsidian.md/t/vaultsearch-local-first-hybrid-search-bm25-semantic-fuzzy/113134), [Hybrid Search MCP thread](https://forum.obsidian.md/t/hybrid-search-hybrid-search-mcp-server-cli-for-ai-assistants-bm25-semantic-obsidian-native/112491))
- Multi-hop-via-backlinks: can graph traversal (2-hop backlink following) answer a question that requires connecting two notes — this is a genuinely fair analogue to iranti's `iranti_related`/`iranti_related_deep` graph-traversal tools
- Latency and local storage footprint for a fixed vault size
- A community MCP bridge (MCP Tools, obsidian-mcp-server, Nooscope) gives Obsidian a `search`/`read` tool surface an agent can call exactly like it calls iranti's MCP tools — so the *access pattern* comparison (agent calls a tool, gets text back) is fair

**Not fair to test (Obsidian has no mechanism at all, so scoring it 0% here is a category error, not a finding):**
- Auto-extraction from conversational prose (Obsidian never watches a conversation and writes a note on its own — a human or a separate LLM-in-the-loop plugin like Smart Connections/Copilot-for-Obsidian would have to do that, which then benchmarks the *plugin*, not Obsidian)
- Fabrication rate / extraction precision on unstructured input (nothing to measure — there is no auto-writer)
- Abstention/no-answer honesty in the iranti sense (Obsidian's search returns "no results," which is a different signal than an LLM asserting false confidence — don't conflate "empty result set" with "correctly declined to answer")
- Rules/standing-preference injection at the moment it matters (no situational-relevance engine exists in stock Obsidian)
- Determinism-under-repeated-run in the LLM-judge sense (Obsidian's BM25 ranking IS deterministic, which is actually a point in its favor to disclose, not a gap)

**How to actually run it:** author one shared corpus (the same facts/personas as iranti's `bench/corpus/*.json`) as Obsidian notes with wikilinks for entity references; run the same probe queries from `CorpusProbe.query` through Obsidian's search (or a community MCP bridge's `search` tool) instead of `iranti_query`/`iranti_attend`; score hit-rate/rank exactly as `scorer.ts` does today. Label the resulting row "Obsidian (retrieval-only slice)" everywhere it appears, never "Obsidian (full comparison)."

## (c) Recommended minimal fair suite — 3–4 methods, most decision value per unit effort

Given the plan's fairness mandate ("same corpus + same judge + same inputs for every system... self-reported vendor numbers flagged as such and re-run locally where possible"), the goal is not maximum coverage — it's the smallest set that (1) can actually be run against all 8 systems without contorting any of them, (2) reuses existing, defensible judge prompts rather than inventing new ones, and (3) gives iranti a number on the same public scale competitors already publish, so any gap or lead is legible to an outside reader.

1. **LongMemEval-S** (method #2) — *primary apples-to-apples anchor.* Reasons: (i) it is the smaller/cheaper of the two peer-reviewed anchors (~115K tokens vs. LoCoMo's need for full 10-conversation ingestion, and far cheaper than LongMemEval-M's ~1.5M tokens); (ii) its **abstention** category is a direct, already-instrumented match for iranti's `falsePositiveRate` — no new scoring code needed, just a new corpus source; (iii) every named competitor already reports on it or a close cousin, so a shared number is directly comparable and hard to dismiss as "iranti graded its own homework."
2. **LoCoMo** (method #1) — *the number everyone else already quotes.* Even with its known target-noninvariance and category-5-accounting fragility (documented below), skipping it entirely would make the report look evasive — "why doesn't iranti have a LoCoMo number" is the first question any reader familiar with Mem0/Zep/ByteRover's marketing will ask. Reuse ByteRover's open-sourced [brv-bench](https://github.com/campfirein/brv-bench) judge/justifier prompts (it explicitly supports a `--context-tree-source` flag for plugging in an arbitrary system) rather than writing a new judge from scratch — this closes the "which judge, which prompt" fairness gap by construction, since it's the same prompt ByteRover, Hindsight, Memobase, HonCho, Zep, and Mem0 numbers were already produced with.
3. **DMR — Deep Memory Retrieval** (method #4) — *cheap floor/sanity check.* 500 short conversations, single-turn retrieval, no elaborate judge needed beyond a simple correctness check. Costs almost nothing to run against all 8 systems (including Obsidian, trivially) and catches any system that can't even do the simplest cross-session recall before spending money on the harder tests. Use it as a pre-flight gate, not a headline number.
4. **iranti's own coding-continuity methodology** (method #12, specified fully in §d) — *the differentiator, on a clearly separate axis.* This is the one test where iranti is not grading itself on someone else's rubric, and it directly operationalizes the plan's mandate that "iranti's coding-memory edge is shown on a SEPARATE, clearly-labeled axis, not by tilting the shared tasks." Every competitor gets run against it under the identical protocol — including Obsidian, scored honestly as "no mechanism" rather than skipped.

**Explicitly excluded from the minimal suite, with reasons:** LongMemEval-V2 and BEAM-10M (wrong shape / cost-prohibitive for this comparison, see table rows 3 and 8 — hold as stage-2 stretch goals); MemoryArena and MemBench (valuable as design templates, but MemBench's scoring formula is unconfirmed from available sources and MemoryArena requires an action-taking harness incompatible with Obsidian — both noted as "read the full PDF before building" follow-ups, not blocking); HotpotQA-as-memory and NIAH/passkey (low marginal value — NIAH is worth keeping only as a cheap CI regression gate, not a comparison headline).

## (d) Coding-memory methodology spec — detailed enough to build

### Why this is the right home-field test

No benchmark in this catalogue tests **cross-session continuity within a single coding task** — SWE-ContextBench tests cross-*task* trajectory reuse (task A informs task B), and every persistent-memory CLI-agent survey found in this research (Aider, Cline, Gemini CLI, Codex CLI, OpenCode) confirms "a clear division exists between agents designed for benchmark evaluation and those designed for interactive use," with the benchmark-evaluation agents (SWE-agent, OpenHands, AutoCodeRover, mini-swe-agent, DARS-Agent) treating every task as a fresh, memoryless episode by design. One survey source ([firecrawl.dev / tessl.io coverage](https://tessl.io/blog/8-benchmarks-shaping-the-next-generation-of-ai-agents/)) independently reports the concrete cost of this gap: developers estimate **15–25% of interaction time with a coding agent is spent re-establishing context** it should already have. That number is the business case for this test existing at all.

### The exact test structure

**Unit of measurement: a "continuity probe."** One probe = one (decision-or-constraint, session-1 message that establishes it, session-2 message that should be affected by it, pass/fail rule).

**Step 1 — Task selection.** Pick or construct N (start with N=15–20) realistic coding tasks that naturally span more than one sitting — e.g., "add rate limiting to the API," "migrate the ORM," "fix the flaky auth test." Real repos are better than synthetic ones (use iranti's own repo, or a small set of open-source repos with real, messy history) because the point is to test memory under authentic ambiguity, not a scripted fact.

**Step 2 — Session 1: establish.** In a fresh memory-store session, have the agent (or a scripted persona, to keep this reproducible — see iranti's own `bench/corpus/*.json` convention of fixed, versioned transcripts) do real work on the task and, along the way, **naturally** state 2–4 of the following per task:
- a **decision** ("we're using Postgres + Drizzle for this, not Prisma")
- a **constraint** ("never use `SELECT *` in the reporting queries")
- a **rejected/failed approach** ("we tried a unique-constraint approach for idempotency and it broke under retries")
- a **correction** ("actually, the pool size is 20, not 10 — I misspoke earlier")

Phrasing must be conversational, not keyword-engineered — this is exactly the failure mode iranti's own corpus-growth policy already guards against (`bench/corpus/README.md`'s "author fresh sentences without looking at the pattern list" discipline) and it must be enforced here too, or the test measures keyword-matching instead of memory.

**Step 3 — the gap.** Close the session. Simulate a real gap (hours to days — pick a consistent value across all systems being compared, e.g. "next calendar day"), during which unrelated work may happen (other tasks, other repos) to test that the fact doesn't just survive by being the only thing in context.

**Step 4 — Session 2: the moment it matters.** Open a **new** session on the **same task** (same repo/folder scope) and present a message that would be answered *differently* depending on whether the session-1 fact is honored — critically, the session-2 message must **not** restate or hint at the fact; it must be a naturalistic continuation that only makes sense if the constraint/decision is still "in the room." Three concrete probe shapes:
1. **Direct-collision probe:** the agent (or a scripted continuation) is about to violate the constraint (writes a `SELECT *`, picks Prisma, re-tries the already-failed idempotency approach) — pass = memory surfaces the standing fact *before or at* the moment of violation, not after being asked.
2. **Silent-confirmation probe:** ask a question whose answer IS the session-1 fact, phrased as if the asker forgot ("what are we using for the DB layer again?") — pass = correct answer, at high rank, with no re-derivation (this reuses iranti's existing `confirmationRate`/rank-1 concept from `scorer.ts` directly).
3. **Negative/no-bleed probe:** ask about a DIFFERENT, unrelated task in a DIFFERENT folder/project scope, using vocabulary that's superficially similar — pass = the session-1 fact does NOT leak in (this is the same shape as iranti's `CorpusProbe.negative`/`falsePositiveRate`, applied cross-project instead of cross-question).

**Step 5 — scoring.** Three numbers, cheap to compute and directly comparable across all 8 systems:
- **Continuity recall** = (probes where the fact correctly surfaced in session 2) / (total established facts) — the headline number.
- **Precision-at-the-moment** = of the direct-collision probes, what fraction surfaced the constraint *before* the violating action was taken vs. only after being asked afterward (a system that only answers when interrogated, never proactively, should score lower here even if raw recall is fine — this operationalizes the "confirm, don't discover" principle already in iranti's own dogfood-eval philosophy, `docs/rough-notes/dogfood-eval-prompt.md`).
- **Cross-task bleed rate** = false-positive rate on the negative/no-bleed probes — reuses the exact `falsePositiveRate` computation already in `src/harness/scorer.ts`.

**Step 6 — running it against a competitor on the same inputs.** For each of Mem0/Zep/ByteRover/Shodh/ai-mem/Obsidian: (1) feed the identical session-1 transcript through that system's write/ingest API (or, for Obsidian, have a human write the equivalent note — and *label* that difference, don't hide it); (2) after the identical gap, issue the identical session-2 probe message through that system's query/retrieval API; (3) score with the identical pass/fail rule above, no judge-prompt customization per system. This is the same discipline the plan already commits to ("same corpus + same judge + same inputs for every system") — the only per-system work is a thin ingest/query adapter, which the plan's S3 stage already scopes as "one at a time, cheapest-first."

**Why this is fair to Obsidian too:** a human (or a scripted note-writer standing in for one) writes the session-1 facts as vault notes; session 2 is a search/backlink query. Obsidian will very likely score *well* on continuity recall (a human wrote it down, it's there, BM25 can find it) but will structurally score **zero** on anything upstream of that — it never "hears" the conversation and decides on its own what's worth keeping. That's the correct, honest result, not a bug in the test: it isolates *retrieval-given-that-someone-remembered-to-write-it-down* (Obsidian's real capability) from *deciding-what's-worth-remembering-without-being-told* (iranti's actual thesis, per `docs/research/competitive-landscape.md`'s "autonomous... decides what to remember without being told" framing). Report both numbers side by side, not collapsed into one score.

**Cost to build:** the transcript/probe authoring convention is a direct extension of iranti's existing `Corpus`/`CorpusProbe`/`GoldFact` types (`src/harness/types.ts`) — this is not a new file format, it's a new *field* (`sessionBoundary: number` marking where session 1 ends and the gap begins) on the existing corpus shape, plus a scorer function that filters probes by which side of the boundary they're on. Estimate: small to medium — most of the machinery (probe running, hit/rank scoring, negative-probe false-positive scoring) already exists and is being reused, not invented.

| Axis | Definition | Already in iranti? |
|---|---|---|
| **Retrieval precision/recall/F1@k** | Standard IR metrics at a fixed k (e.g. k=5 or k=10) — of the k results returned, how many are relevant (precision), and of all relevant items, how many were in the top-k (recall) | Partially — iranti's harness reports hit-rate/confirmation-rate (effectively precision/recall@k with k = the full returned `facts[]` array) but does not currently sweep multiple k values; adding a k-sweep is a small extension to `scorer.ts` |
| **Extraction precision/recall — value-based, not key-based** | Credit a stored fact if its *value* matches a gold value, regardless of what key/label it was filed under — the brief's explicit ask, because two extractors can correctly capture the same fact under different internal names | **Yes, already built** — this is exactly iranti's `valueRecall`/`valueRecallCount` metric in `src/harness/scorer.ts`, added specifically to credit LLM extraction that files a fact under a different key than the heuristic extractor's synthesized one |
| **Latency** | Wall-clock time from query issued to answer returned, per operation type (write/ingest vs. read/query) | Partially — dogfood notes mention felt latency qualitatively; no automated per-call latency histogram yet in the harness |
| **Token/$ cost per operation** | LLM tokens (and $ at current pricing) consumed per write and per query — critical because several competitors (ByteRover, Mem0) explicitly market token-efficiency numbers (e.g. Mem0's "<7,000 tokens per retrieval vs. 25,000+ for full-context") that need independent verification the same way accuracy numbers do | Not yet instrumented — would need a token-counting wrapper around any LLM calls in the extraction/retrieval path |
| **Storage footprint** | Disk/DB size for a fixed corpus size — relevant for comparing a lightweight embedded store (iranti-next, Shodh's 30MB binary) against heavier vector-DB-backed systems | Not yet instrumented |
| **Determinism/reproducibility** | Running the identical input twice produces byte-identical (or metric-identical) output | **Yes, already built and enforced** — `harness.test.ts` diffs two full report JSONs; the dogfood-eval prompt explicitly bars running `pnpm bench` twice and checking for byte-identical metrics as check #12 |
| **Abstention/hallucination rate** | Does the system correctly decline to answer when the answer isn't in its store, vs. confidently fabricating one | **Yes, already built** — `falsePositiveRate`/`falsePositiveRateRaw` on negative probes (`CorpusProbe.negative`), plus the separate `fabricationRate` on `FabricationProbe`s that must yield zero extracted facts. This is a genuine point of instrument maturity relative to the field: LongMemEval's abstention category is the closest published equivalent, and iranti already has *two* distinct mechanisms (retrieval-side false-positive, extraction-side fabrication) where most published benchmarks have one |

**Note on why this matters for adversarial verification specifically:** several of the disputed vendor numbers found in this research (Zep's corrected 84%→58.44%, MemPalace's top_k=50-vs-32-candidate-pool disclosure) trace back to exactly these cross-cutting axes being left implicit — an undefined scoring target, an unstated retrieval-window size. The 2026 methodology critique paper on "target noninvariance" ([arXiv 2605.24060](https://arxiv.org/html/2605.24060v1)) makes this the paper's central thesis: benchmarks that don't publish their exact scoring target, k value, and judge prompt are not independently reproducible even when everyone quotes the same benchmark name. Every method run for the competitive-benchmark program should publish all of these axes alongside the headline accuracy number, not just the accuracy number.
