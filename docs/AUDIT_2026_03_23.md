## C-2 — Infinite HTTP redirect loop in `httpsJson()`

**File:** `scripts/iranti-cli.ts`
**Lines:** 2615–2648

**What is happening:**
```typescript
if (statusCode >= 300 && statusCode < 400 && response.headers.location) {
    response.resume();
    const redirect = new URL(response.headers.location, url).toString();
    httpsJson(redirect, headers).then(resolve).catch(reject); // no depth limit
    return;
}
```
The function calls itself recursively for every redirect response with no counter or limit. A server that responds with a redirect loop (or a DNS-hijacked npm/PyPI registry) causes unbounded stack growth and an eventual crash.

**Why it is an issue:**
This function is called during `iranti upgrade --check` and `iranti upgrade` to fetch the latest version from npm and PyPI registries. A malicious or misconfigured registry (or a captive portal intercepting HTTPS) can trigger this. The crash is a denial-of-service against the CLI process.

**Affected files / functions:**
- `scripts/iranti-cli.ts` — `httpsJson()` lines 2615–2648
- `fetchLatestNpmVersion()` line 2650 — calls `httpsJson`
- `fetchLatestPypiVersion()` line 2659 — calls `httpsJson`
- `upgradeCommand()` — calls both of the above

**Fix plan:**
Add a `depth` parameter defaulting to `0`, reject after `10` hops:
```typescript
function httpsJson(url: string, headers: Record<string, string> = {}, depth = 0): Promise<any> {
    if (depth > 10) return Promise.reject(new Error(`Too many redirects fetching ${url}`));
    // ... on redirect:
    httpsJson(redirect, headers, depth + 1).then(resolve).catch(reject);
}
```
Also add a request timeout (30s) using `req.setTimeout()` to prevent indefinite hangs on slow registries.

**Testing strategy:**
- Unit test: mock `https.get` to return 302 → 302 → ... (n times); verify error thrown after 10 hops
- Unit test: mock slow response; verify timeout fires
- Integration: run `iranti upgrade --check` against a local mock server that redirects infinitely

## C-3 — Windows command injection in `quoteForCmd()`

**File:** `scripts/iranti-cli.ts`
**Lines:** 2269–2273

**What is happening:**
```typescript
function quoteForCmd(arg: string): string {
    if (arg.length === 0) return '""';
    if (!/[ \t"&()<>|^]/.test(arg)) return arg;
    return `"${arg.replace(/"/g, '\\"')}"`;
}
```
The function escapes double-quotes but does not handle `%` (CMD variable expansion), `!` (delayed expansion), or `^` when it appears inside a quoted string in certain CMD contexts. Arguments are then joined with `.join(' ')` and executed via `cmd.exe /c "..."` — the string is parsed by CMD's shell, not by the process directly.

**Example attack:** A user-supplied argument containing `%COMSPEC%` or `%PATH%` would be expanded by CMD before being passed to the target process.

**Why it is an issue:**
This function is used in `runCommandCapture()` and throughout the Windows upgrade/uninstall flows where arguments can include user-provided values: instance names, port numbers, database URLs, passwords, and file paths.

**Affected files / functions:**
- `scripts/iranti-cli.ts` — `quoteForCmd()` lines 2269–2273
- `runCommandCapture()` lines 2290+
- `runDockerPostgresContainer()` lines 1713–1765 (joins Docker args with `quoteForCmd` on Windows)
- `scheduleDetachedWindowsGlobalNpmUpgrade()` lines 2979–2996
- `buildDetachedWindowsUninstallScript()` lines 3389–3422

**Fix plan:**
The correct fix is to stop joining arguments into a shell string entirely on Windows. Use the array-based form of `spawnSync`/`spawn` with `shell: false` everywhere. For the cases where `cmd.exe /c` is genuinely needed, use the `args` array rather than a joined string:
```typescript
// Instead of:
spawnSync(ComSpec, ['/d', '/c', args.map(quoteForCmd).join(' ')], ...)

// Use:
spawnSync(executable, args, { shell: false, ... })
```
Where `cmd.exe /c` is unavoidable (e.g., `.cmd` shims), use `child_process.execFile` with explicit argument arrays, not `exec`.

**Testing strategy:**
- Unit test `quoteForCmd` with: `%TEMP%`, `!var!`, `^&whoami`, `"quoted"`, paths with spaces, empty string, unicode characters
- Integration test on a real Windows machine: pass each of those as an argument and verify the downstream process receives the literal string, not the expanded value
- Audit every call site of `quoteForCmd` and replace with shell-free spawn

## C-4 — Concurrent writes to env files cause silent data loss

**File:** `scripts/iranti-cli.ts`
**Lines:** 582–628 (`upsertEnvFile`)

**What is happening:**
```typescript
async function upsertEnvFile(filePath: string, updates: Record<string, string | undefined>): Promise<void> {
    const existingRaw = fs.existsSync(filePath) ? await fsp.readFile(filePath, 'utf-8') : '';
    // ... modify in memory ...
    await writeText(filePath, `${finalLines}\n`); // direct overwrite
}
```
There is no file lock, no exclusive open, and no atomic rename. Two CLI processes running simultaneously (e.g., the user runs `iranti add api-key openai` in one terminal and `iranti configure instance` in another) will both read the same file at T=0, each modify their in-memory copy independently, and then whichever finishes last will overwrite the other's changes — silently.

**Why it is an issue:**
This function is called by virtually every write-path command. API keys, database URLs, instance configuration, and project bindings can all be silently lost. The user has no indication anything went wrong.

**Affected files / functions:**
- `scripts/iranti-cli.ts` — `upsertEnvFile()` lines 582–628
- `writeText()` line 509 — no atomic write
- `writeProjectBinding()` lines 850–859
- `configureInstanceCommand()` — calls `upsertEnvFile`
- `configureProjectCommand()` — calls `upsertEnvFile`
- `upsertProviderKeyCommand()` — calls `upsertEnvFile`
- `removeProviderKeyCommand()` — calls `upsertEnvFile`
- `setupCommand()` — calls `upsertEnvFile`

**Fix plan:**
Two complementary approaches:

1. **Atomic write:** Write to `filePath + '.tmp'`, then `fs.rename(tmpPath, filePath)`. On most OSes (including Windows via `MoveFileEx` with `MOVEFILE_REPLACE_EXISTING`) this is atomic at the filesystem level.

2. **Advisory lock:** Before read-modify-write, acquire a lock file at `filePath + '.lock'` using a library like `proper-lockfile`, or implement manually with `open(O_CREAT | O_EXCL)`. Release on completion or error.

Both should be used together. The lock prevents the race; the atomic rename prevents corruption if the process crashes mid-write.

**Testing strategy:**
- Concurrency test: spawn 10 simultaneous CLI processes each adding a different key to the same env file; verify all 10 keys are present in the result
- Crash test: kill the process during `writeText` and verify the file is either fully intact or fully old (never partial)
- Verify on Windows (rename semantics differ) and Linux

## C-5 — PowerShell `postCommand` injected without escaping

**File:** `scripts/iranti-cli.ts`
**Lines:** 2979–2996

**What is happening:**
```typescript
...(postCommand ? [`if ($LASTEXITCODE -eq 0) { ${postCommand} }`] : []),
```
`postCommand` is a string parameter that is embedded directly into the body of a generated PowerShell script without any escaping or sanitization.

**Why it is an issue:**
Any PowerShell metacharacter in `postCommand` executes as code. Even though the current callers pass internal-only strings, the pattern creates a footgun: future callers (or a refactor that threads user input through) will introduce arbitrary code execution. The generated script is then run detached as the current user.

**Affected files / functions:**
- `scripts/iranti-cli.ts` — `scheduleDetachedWindowsGlobalNpmUpgrade()` lines 2979–2996
- `buildDetachedWindowsUpgradeScript()` lines 2960–2977
- Any future caller that passes `postCommand`

**Fix plan:**
Either:
- Remove the `postCommand` parameter entirely and handle post-upgrade steps as separate explicitly-typed script lines built from safe primitives; or
- Wrap `postCommand` through `escapeForSingleQuotedPowerShell()` and embed it inside a single-quoted string that is then invoked via `Invoke-Expression` with appropriate restrictions

Prefer the first option — post-upgrade steps are known at development time and should be expressed as structured script lines, not arbitrary strings.

**Testing strategy:**
- Unit test: pass `postCommand = 'Write-Host "injected"; Stop-Computer'` and verify it does not execute
- Verify the generated `.ps1` file on disk contains the expected content before each test run

## H-1 — `archiveEntry()` is not wrapped in a transaction

**File:** `src/library/queries.ts`
**Lines:** 644–657

**What is happening:**
The soft-delete function calls `insertArchiveFromCurrent()` (copies the live row to the archive table) and then `deleteEntryById()` (removes it from the live table) as two separate database calls with no wrapping transaction.

**Why it is an issue:**
If the process crashes or the database connection drops between the two calls, the entry exists in both tables simultaneously. Subsequent reads of the live table return data that should have been archived. Subsequent archive reads may also return a duplicate.

**Affected files / functions:**
- `src/library/queries.ts` — `archiveEntry()` lines 644–657
- `insertArchiveFromCurrent()` — called first
- `deleteEntryById()` — called second
- `src/librarian/index.ts` — calls `archiveEntry` during write decisions

**Fix plan:**
Wrap both calls in a Prisma interactive transaction:
```typescript
async function archiveEntry(tx: PrismaClient, id: number): Promise<void> {
    await tx.$transaction(async (txClient) => {
        await insertArchiveFromCurrent(txClient, id);
        await deleteEntryById(txClient, id);
    });
}
```
All callers that currently pass a transaction client should continue to do so; callers that pass the top-level Prisma client will get automatic transaction wrapping.

**Testing strategy:**
- Simulate a crash between the two calls (e.g., by mocking `deleteEntryById` to throw) and verify the archive insert was rolled back
- Verify that after a successful `archiveEntry`, the entry does not appear in the live table and appears exactly once in the archive table

**What is happening:**

const rawDepth = parseInt(req.query.depth as string ?? '2', 10);
const depth = Number.isFinite(rawDepth) && rawDepth > 0 ? Math.min(rawDepth, 5) : 2;

## H-7 — Setup has no cleanup on interrupt (SIGINT)

**File:** `scripts/iranti-cli.ts`
**Lines:** 1767–1851

**What is happening:**
`executeSetupPlan()` creates directories, writes config files, starts Docker containers, creates databases, and writes project bindings in sequence. There is no SIGINT handler that rolls back completed steps if the user cancels.

**Why it is an issue:**
A user who cancels mid-setup (or whose process is killed) is left with a partial installation: some directories exist, a Docker container may be running, a database may exist with no schema, and project `.env.iranti` files may point to a non-functional instance. A subsequent `iranti setup` attempt may fail or behave unpredictably.

**Affected files / functions:**
- `scripts/iranti-cli.ts` — `executeSetupPlan()` lines 1767–1851
- `setupCommand()` — calls `executeSetupPlan`
- `createInstanceCommand()` — similar create flow without cleanup
- All functions called within setup: `ensureDir`, `writeInstanceEnv`, `runDockerPostgresContainer`, `runBundledScript('setup', ...)`, `writeProjectBinding`

**Fix plan:**
Implement a rollback stack:
```typescript
const rollback: Array<() => Promise<void>> = [];
process.on('SIGINT', async () => {
    console.log('\nSetup interrupted. Rolling back...');
    for (const fn of rollback.reverse()) {
        try { await fn(); } catch { /* log and continue */ }
    }
    process.exit(1);
});
// Before each step:
rollback.push(async () => await fsp.rm(instanceDir, { recursive: true, force: true }));
await ensureDir(instanceDir);
```
The rollback stack is built progressively; each push happens immediately before the corresponding action so the cleanup mirrors the creation order in reverse.

**Testing strategy:**
- Send SIGINT at each distinct step (after dir creation, after env write, after Docker start, after DB creation) and verify the state is fully cleaned up
- Verify that a clean `iranti setup` succeeds after each interrupted run

## H-8 — Missing foreign keys on `Archive` and `EntityRelationship` tables

**File:** `prisma/schema.prisma` and migrations
**Lines:** `schema.prisma:79–82` (Archive), `90–104` (EntityRelationship)

**What is happening:**
`Archive.supersededBy`, `supersededByEntityType`, `supersededByEntityId`, and `supersededByKey` reference data in `KnowledgeEntry` but have no foreign key constraint. `EntityRelationship.fromType`/`fromId`/`toType`/`toId` reference `Entity` but also have no FK.

**Why it is an issue:**
When a `KnowledgeEntry` or `Entity` is deleted, all referencing rows in `Archive` and `EntityRelationship` become orphaned. Queries that join on these fields return incorrect or missing data. The database cannot enforce referential integrity.

**Affected files / functions:**
- `prisma/schema.prisma` — Archive model lines 79–82, EntityRelationship model lines 90–104
- `src/library/queries.ts` — any query that reads `Archive.supersededBy*`
- `src/library/relationships.ts` — all relationship queries
- All migrations going forward (this needs a new migration)

**Fix plan:**
Add a new migration:
```sql
-- Archive: add FK to KnowledgeEntry on (entityType, entityId) with CASCADE
ALTER TABLE "Archive" ADD CONSTRAINT "Archive_entity_fkey"
  FOREIGN KEY ("entityType", "entityId")
  REFERENCES "KnowledgeEntry"("entityType", "entityId")
  ON DELETE CASCADE;

-- EntityRelationship: add FK to Entity on (fromType, fromId)
ALTER TABLE "EntityRelationship" ADD CONSTRAINT "EntityRelationship_from_fkey"
  FOREIGN KEY ("fromType", "fromId")
  REFERENCES "Entity"("entityType", "entityId")
  ON DELETE CASCADE;

-- EntityRelationship: add FK on (toType, toId)
ALTER TABLE "EntityRelationship" ADD CONSTRAINT "EntityRelationship_to_fkey"
  FOREIGN KEY ("toType", "toId")
  REFERENCES "Entity"("entityType", "entityId")
  ON DELETE CASCADE;
```
Before adding: audit for existing orphaned rows and clean them up. The migration will fail if orphans exist.

**Testing strategy:**
- Delete an entity and verify all its archive rows and relationships are also deleted
- Attempt to insert an `EntityRelationship` referencing a non-existent entity and verify the FK violation is raised
- Run the migration against a copy of production data to catch existing orphans before applying to production
